# Spec/Impl Module Boundaries

- Separate exported contracts from implementation details inside every business module, including implementation/helper modules and retained contract projects. Follow the [canonical public/actual rule](kmp-spec-impl-source-sets.md#source-set-responsibilities): only `specMain` declares public APIs; other production source sets provide corresponding public `actual` implementations or effectively internal/private declarations. An implementation role is not an exemption, and an empty `specMain` requires no module-owned export needing a declaration there.
- Follow the [canonical project naming and boundary rules](kmp-spec-impl-source-sets.md#project-naming-and-boundaries): Gradle business project IDs and module directory paths do not use `spec` or `impl` classification segments. Removing directory categories does not merge View/ViewModel or composition responsibilities. A genuinely necessary cycle-breaking contract project is named `contract` and still places its contracts in `specMain`; historical boundaries or multiple consumers alone do not justify retaining a split.
- Independent models, codecs, transports, and helpers use business names, not a blanket `spec` → `contract` rename. Existing platform coverage and real dependency constraints must be preserved when selecting consolidation units. Current legacy paths are pending scoped migration, not an approved target layout.
- Every implementation unit must have a corresponding, meaningful specification, whether in its own project or the selected source-set structure. When no contract can be identified, reconsider the boundary rather than create an empty interface, marker type, or copied DTO.
- A spec is the authoritative source for its code-level contract **and the KDoc attached to that contract**: values, operations, observable states, lifecycle and error semantics, and compatibility guarantees.
- Document contractually observable exceptions on the throwing spec operation with KDoc `@throws`, including the condition that triggers each exception; do not leave that behavior documented only on an implementation or exception class.
- Implementation code may carry KDoc for its concrete behavior and mechanism. That KDoc is not a second normative source and must not contradict the spec; do not remove it merely because a spec exists.
- Move KDoc with declarations that move. When extracting a spec interface from concrete code, state cross-implementation guarantees on the spec; retain implementation-specific details with the implementation.
- Cross-module declaration references are `spec -> spec` or `impl -> spec`. Implementation business modules may compose other implementation modules, but must call their exported spec APIs rather than implementation-only declarations. A combined project/artifact does not relax this boundary. Track remaining direct implementation references as migration gaps, not as composition exemptions.
- Preserve persisted and RPC serialization shapes, ownership, and behavior during module migration. A necessary contract or wire change requires its own review rather than being hidden in a move.
- Component migrations are hard cutovers: move the real ViewModel contract and implementation, remove the replaced declarations, and update all consumers. Do not introduce a parallel public model plus adapter, resolver, alias, or forwarding project merely to compile against the old host. Ordinary storage/RPC dependency binding and renderer-local visual composition remain valid boundaries.
